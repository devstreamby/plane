# Аватарки пропадают из профиля после входа через AD

**Status:** fixed 2026-08-28 on `fix/ldap-sync-wipes-user-avatar`. Найден
2026-08-28 после жалобы, что аватарки исчезли у всех — предположительно после
передеплоя прода.

## Симптом

Пользователь загружает аватар через профиль, он отображается. Через некоторое
время аватар пропадает — в профиле снова заглушка с инициалами. Загрузка нового
аватара помогает ненадолго, потом он исчезает снова.

На проде (`plane.devstream.by`) из 12 участников воркспейса аватар остался ровно
у одного: у 11 в БД `avatar_asset = NULL` и `avatar = ''`.

## Что оказалось ни при чём

Хранилище цело. Уцелевший аватар отдаётся штатно:
`/api/assets/v2/static/{id}/` → 302 → presigned URL MinIO → 200, `image/jpeg`,
13 КБ. То есть ни MinIO, ни бакет, ни путь отдачи, ни presigned-подпись к делу
не относятся — теряются именно ссылки в БД.

Передеплой тоже не причина, хотя корреляция настоящая: он сбрасывает сессии,
все логинятся заново, и баг срабатывает у всех разом. Отсюда впечатление
одномоментной пропажи.

## Причина

`Adapter.sync_user_data()`
([apps/api/plane/authentication/adapter/base.py:306](../../apps/api/plane/authentication/adapter/base.py))
выполняется при **каждом** входе через провайдера, если включена
IDP-синхронизация. До исправления код был такой:

```python
avatar = self.user_data.get("user", {}).get("avatar", "")
self.delete_old_avatar(user=user)          # безусловно, до проверки замены
avatar_asset = self.download_and_upload_avatar(avatar_url=avatar, user=user)
if avatar_asset:
    user.avatar_asset = avatar_asset
else:
    user.avatar = avatar                    # "" — ничего не восстановлено
```

Три обстоятельства складываются в потерю данных:

1. **`delete_old_avatar()` вызывается безусловно** — до того, как выяснилось,
   есть ли чем заменить. Она удаляет объект из хранилища
   (`storage.delete_files(...)`), удаляет запись `FileAsset` и ставит
   `avatar_asset = None`, `avatar = ""`. Поле `User.avatar_asset` объявлено с
   `on_delete=models.SET_NULL`, так что ссылка обнуляется в любом случае.
2. **LDAP-провайдер никогда не отдаёт аватар** — в
   [ldap.py:105](../../apps/api/plane/authentication/provider/credentials/ldap.py)
   поле захардкожено как `"avatar": ""`. Значит
   `download_and_upload_avatar("")` возвращает `None` на первой же строке
   (`if not avatar_url: return None`), и восстанавливать нечего.
3. **`ENABLE_LDAP_SYNC` по умолчанию `"1"`** — для `ldap` дефолт включённый, в
   отличие от остальных провайдеров, у которых `"0"`
   ([base.py:145](../../apps/api/plane/authentication/adapter/base.py)).

Итог: каждый вход через AD безвозвратно уничтожал загруженный пользователем
аватар — вместе с файлом в объектном хранилище.

Показательно, что путь **регистрации** в том же файле написан правильно: там
стоит `if avatar:` перед всей операцией. Защиты не хватало только в пути
синхронизации.

## Исправление

Трогать аватар только когда провайдер действительно его прислал — то есть
привести путь синхронизации к той же форме, что и путь регистрации:

```python
avatar = self.user_data.get("user", {}).get("avatar", "")
if avatar:
    self.delete_old_avatar(user=user)
    ...
```

Поведение для провайдеров, которые аватар присылают (Google, GitHub, GitLab,
Gitea), не меняется: старый аватар по-прежнему заменяется новым, а при неудачной
загрузке по-прежнему записывается исходный URL.

## Тесты

[test_adapter_avatar_sync.py](../../apps/api/plane/tests/unit/authentication/test_adapter_avatar_sync.py) —
6 тестов. Три регрессионных (провайдер не прислал аватар / ключа `avatar` нет
вовсе / полноценный вход по LDAP не стирает аватар) и три на сохранение
поведения (замена аватара, откат на URL при неудачной загрузке, синхронизация
остальных полей продолжает работать).

Проверено, что тесты действительно ловят баг: на исходном коде падают ровно три
регрессионных, три остальных проходят.

```bash
docker compose -f docker-compose-test.yml run --rm api-tests pytest plane/tests/unit/authentication/test_adapter_avatar_sync.py -v
```

## Последствия для данных

Утраченные аватарки восстановить нельзя: `delete_old_avatar()` удаляет и сам
файл из MinIO, а не только ссылку. После деплоя исправления пользователям нужно
загрузить аватар заново — теперь он переживёт вход через AD.
